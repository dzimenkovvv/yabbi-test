# mini-AdEx — роутер аукционных запросов

Упрощённый сервис рекламной биржи: принимает запрос на аукцион,
отбирает подходящих DSP-партнёров (претаргетинг) и параллельно
рассылает им запрос с общим таймаутом.

Стек: Go, только стандартная библиотека для HTTP (`net/http`).
`testify` подключён исключительно для тестов.

## Как запустить

```bash
go mod tidy
go run ./cmd/server
```

Сервер поднимется на `:8080` и выведет структурированный JSON-лог:

```json
{"time":"...","level":"INFO","msg":"starting server","addr":":8080"}
```

Тесты:

```bash
go test -race ./...
```

Юнит-тесты обязательно с флагом `-race` — в `internal/auction/dispatcher.go`
это единственный способ реально проверить корректность параллельной
рассылки, а не только то, что код компилируется.

## Пример запроса, на котором видна фильтрация

В `internal/partner/store.go` захардкожено 4 партнёра с разными условиями:
`dsp-alpha` (RU/KZ, floor 0.5), `dsp-beta` (любая страна, но floor 2.0),
`dsp-gamma` (RU/US/DE, любое устройство, без ограничений), `dsp-delta`
(отключён — `is_enabled: false`).

```bash
curl -X POST http://localhost:8080/auction \
  -H "Content-Type: application/json" \
  -d '{
    "request_id": "demo-1",
    "country": "RU",
    "device_type": "mobile",
    "bid_floor": 1.0,
    "categories": ["news"]
  }'
```

Ответ:

```json
{"request_id":"demo-1","matched_dsps":["dsp-alpha","dsp-gamma"],"sent":2,"succeeded":2,"duration_ms":0}
```

Из 4 партнёров прошли двое:

- `dsp-alpha` — гео и устройство подходят, `bid_floor` 1.0 ≥ его минимума 0.5.
- `dsp-gamma` — работает с любым устройством, гео подходит, ограничений нет.
- `dsp-beta` отсеялся: `bid_floor` запроса (1.0) ниже его минимума (2.0).
- `dsp-delta` отсеялся: партнёр отключён (`is_enabled: false`), это
  проверяется первым и не зависит от остальных условий.

Причины отсева каждого партнёра логируются на уровне `Debug`
(см. `auction/service.go`) — в проде эти логи первым делом смотрят при
разборе "почему партнёр X не получил трафик".

Если под запрос не подходит ни один партнёр — тоже `200`, но с пустыми
`matched_dsps: []` и `sent: 0` — это штатная ситуация, не ошибка:

```bash
curl -X POST http://localhost:8080/auction \
  -H "Content-Type: application/json" \
  -d '{"request_id":"demo-2","country":"FR","device_type":"tv","bid_floor":0}'
# {"request_id":"demo-2","matched_dsps":[],"sent":0,"succeeded":0,"duration_ms":0}
```

## Где партнёры и как добавить нового

`internal/partner/store.go`. Партнёры изолированы за интерфейсом `Store`:

```go
type Store interface {
    All() []Partner
}
```

Текущая реализация — `InMemoryStore` с захардкоженным слайсом. Чтобы
добавить партнёра, достаточно дописать элемент в слайс внутри
`NewInMemoryStore()` — остальной код (`pretarget.go`, `dispatcher.go`,
`service.go`) ничего не знает про источник данных и не потребует
изменений.

Чтобы переехать на файл/БД — нужно только реализовать `Store` для
нового источника (например, `PostgresStore`) и подставить его в
`cmd/server/main.go` вместо `InMemoryStore`.

## Что бы доделал, будь больше времени

- **Реальный HTTP DSP-клиент.** Сейчас `dsp.Client` — интерфейс с
  единственной реализацией `FakeClient` (осознанно, задание не требует
  реальной интеграции). В проде рядом появилась бы `HTTPClient`,
  реализующая тот же интерфейс — остальной код не изменился бы.
- **Конфигурация через флаги/переменные окружения.** Сейчас адрес,
  таймауты и порт — константы в `main.go`.
- **Healthcheck-эндпоинт** (`GET /health`) и базовые метрики
  (Prometheus: количество запросов, распределение `duration_ms`,
  успешность по партнёрам).
- **Полная валидация `country`** по реальному справочнику ISO
  3166-1 alpha-2, сейчас проверяется только формат (2 заглавные буквы).
- **`store_test.go`** — тривиальный, но фиксирует контракт данных,
  на которые опираются интеграционные тесты в `pretarget_test.go`.
- **Dockerfile / docker-compose** с мок-сервером DSP рядом, чтобы можно
  было гонять `FakeClient`-эквивалент по настоящей сети, а не in-process.
- **`goleak`** в тестах диспетчера вместо эвристической проверки
  повторными запусками — точная проверка отсутствия висящих горутин.

## Структура проекта

```
cmd/server/main.go          — сборка зависимостей, запуск HTTP-сервера
internal/partner/           — модель и хранилище DSP-партнёров
internal/auction/           — претаргетинг, диспатч, сервис, валидация
internal/dsp/                — интерфейс DSP-клиента и фейковая реализация
transport/http/              — HTTP-хендлер (тонкий, без бизнес-логики)
```
